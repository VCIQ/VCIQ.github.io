# 人工决策优先、行为反馈驱动的渐进自动化

状态：用户已明确提出的产品与验收约束；本文的提交不表示运行时代码、数据迁移或部署已完成。

适用仓库：`VCIQ/VCIQ.github.io` 与 `VCIQ/tracking-admin`。

## 一、用户的三项要求

1. 人工明确审核确认后直接生效，不再要求机器先认可或让用户重复审核。
2. 人工追踪、分享、收藏、审核及其历史记录，作为后台的重要反馈依据。
3. 逐步扩大后台可解释、可撤销的自动处理范围，减少人工审核工作量。

仅补齐投资机构目录不能完整满足第 1 项。机器是否已有身份资料与用户是否已作出决定，是两个不同问题。

## 二、决策与执行必须分开

人工决定不是一个可以被模型低分覆盖的普通加权特征。对同一对象、同一作用范围且内容未实质变化的决定，显式人工确认应成为最终决定；机器负责执行、补全和查错，不重新审批。

建议状态含义（是语义约束，具体字段需兼容现有数据）：

| 维度 | 示例 | 含义 |
| --- | --- | --- |
| 人工决定 | approved / rejected / unreviewed | 用户是否已经决定；不由抓取结果或模型分数改写 |
| 执行状态 | queued / running / applied / retryable_failure / blocked | 写入、刷新、发布执行到哪一步 |
| 资料状态 | complete / needs_enrichment / identity_conflict | 资料或实体映射是否完整；不是第二次审核 |

人工确认之后，不得因 `source=unresolved`、缺少目录命中、证据分数不足、抓取超时、提供方失败、构建失败或后续 reconciliation，将该决定退回 unreviewed/review。应保留决定，后台继续补全或重试，并显示具体执行状态。

人工作出的追踪决定允许立即建立持久关注关系，即使对象暂时只有稳定的临时身份。没有正式公司档案，不等于不能关注该对象；不能为了关注而伪造已核验事实。

鉴权、权限、恶意输入、结构完整性、隐私及真实实体冲突等技术保护继续存在。这些是执行保护，而不是同一项人工决定的二次内容审核：例如同名对应两个对象，应保留“已确认关注”，暂停有歧义的实体合并，明确提示冲突对象，只处理该冲突，不要求重审整批。

对人工明确确认的事实或审核范围，保存该范围内的决定及证据版本；关注、分享或收藏一篇文章，不自动等于确认文中每项事实。公开档案的结构、来源归属和部署检查不得被“关注确认”冒充。

人工后续明确撤回或更正，在相同对象与作用范围内覆盖旧决定。自动化不得用旧历史、相似别名、另一赛道的偏好或较高模型分数恢复被忽略、取消或拒绝的关系。重新启用必须有新的明确操作；普通取消收藏仅表示撤回该收藏信号，不等同于拒绝该对象或整个赛道。

## 三、复用现有反馈系统，不另建平行的偏好库

tracking-admin 已有：

- `lib/unified-preference-core.mjs`：统一偏好聚合。
- `lib/unified-preference.ts`：actor-scoped 私有事件读写及人工执行记录。
- `lib/share-preference.ts`：分享信号。
- `lib/manual-preference-history-core.mjs`：历史人工决定。
- `lib/intelligence-resolution.ts`：推荐/解析阶段消费偏好。
- `docs/recommendation-behavior-hierarchy.md`：已有行为强弱约束。

公开仓库已有 `tools/tracking_manual_feedback.py`，用于人工种子、作用域拒绝和来源偏好。两边应协调使用同一语义，不用发布成功率代替用户兴趣。

人工决定优先于加权排序。在推荐排序层，延续“明确追踪 > 分享 > 收藏/稍后看 > 阅读/打开”的语义关系；具体权重通过固定候选回放和留出评估校准，不将任意置信度阈值声称为已校准。

### 行为使用规则

| 行为 | 直接效力 | 后台参考作用 |
| --- | --- | --- |
| 明确确认/追踪 | 对选定对象与范围生效，不再重复询问 | 高优先级种子、主体和赛道偏好 |
| 明确拒绝/忽略/取消追踪 | 在相同范围内阻止自动恢复 | 去噪与负向反馈；不扩展为全局封禁 |
| 分享 | 保存分享行为，不能扩大其授权范围 | 强兴趣/传播价值线索 |
| 收藏/稍后看 | 保存收藏状态 | 持续兴趣与待研究线索 |
| 阅读/打开 | 不改变追踪或审核决定 | 弱参考，不能压过显式决定 |
| 技术失败、排队、缺资料 | 不改变人工决定，不视为用户不喜欢 | 运维重试与资料补全，不生成负向偏好 |

同一操作者、对象、动作及幂等键的重试需要去重；多次网络请求不能被当成多份独立支持。同一文章的分享与收藏可保留不同语义，但不得声称是多个独立事实来源。保留来源、时间、作用范围、规则/模型版本，支持撤回后的重新计算。

原始分享、收藏、审核、个人偏好仍保存在现有私有且按操作者隔离的存储；禁止为方便后台自动化而把私有行为、令牌或身份信息上传到公开 GitHub。浏览器本地历史须经现有授权同步路径导入，不能仅凭代码存在就声称所有历史已经同步。

## 四、逐步减少人工工作，不制造新审批流程

### 阶段 A：消除重复工作并修复已确认状态

自动重试技术失败、合并相同对象的重复待办、按明确且无歧义的身份对齐已确认关系；后台完成来源补全和资料刷新。恢复历史确认必须有可核对的人工记录，不从自动发现列表、运行时数组或模型高分猜测人工确认。

当前风险投资频道的已确认但滞留条目，应沿上述规则修复；剩余尚未人工决定的自动候选不能伪装成人工确认。它们可进入后续自动化策略，而不是要求用户为修复故障重新点一遍全部候选。

### 阶段 B：使用人工反馈进行自动整理和推荐

对抓取资料、候选排序、去重、明确低质噪声隔离等低风险任务自动执行，保留隔离原因和恢复入口。优先显示真正需要补充的具体信息，而不是把机器能查到的字段推回用户。

使用已确认对象、相关赛道、分享和收藏历史的正向关联，也必须核对候选自身身份与相关性。单个弱行为不等于批准；不能为了清空队列机械地批准所有高分候选。

### 阶段 C：有界、可撤销的自动持续关注

先离线/影子回放，再在允许的范围内逐步启用。高确定性的相关候选可以自动进入持续关注，但必须标记 `origin=automatic`，记录依据、规则版本及撤销入口，不能伪造用户操作。存在明确人工否决、身份歧义或证据冲突的候选不得自动覆盖。

自动化批准阈值、批次预算和放量依据来自真实回放与纠错率，不在没有证据时承诺某个固定准确率或减少审核的百分比。持续监测误加、误删、用户撤销、重复审核和队列年龄；出现回归时收紧自动策略，不撤销已有人工决定。

分享和收藏在本需求中是反馈来源，不构成替用户自动对外分享、发消息、发布内容或自动添加收藏的授权。

## 五、必须通过的验收用例

1. 未在目录中的合法对象经授权人工确认后，关注决定立即持久化；显示已确认/待补全，不进入二次审核。
2. 后台重复 reconciliation 或重试后，人工确认仍有效；再读前端不能复现“确认了又回到待审核”。
3. 原人工确认与执行失败分开：接口/抓取/构建失败不会被偏好系统当成拒绝或负面兴趣。
4. 实体名称冲突保留人工决定，仅阻断有风险的合并；不将本人确认从整批丢弃。
5. 同范围的新人工撤回覆盖旧确认；自动候选和旧历史不能复活它。
6. 分享与收藏进入 actor-scoped 偏好聚合并影响相关候选，重试去重；不会自动批准全文实体或事实。
7. 自动执行有明确标识、原因、版本和回滚记录；不能混入人工审核历史并自我强化。
8. 低确定性候选保留为具体异常；不把整个批次退回人工，也不以跳过质量/权限检查制造绿色结果。
9. UI 分别展示已确认、待执行/补全、未确认候选和需处理的具体冲突。旧截图中的总数不能通过隐藏条目冒充修复。
10. 修复需通过完整 CI、真实写入、后续刷新、跨版本/跨会话回读；文档提交或本地预演不算生产验收。
